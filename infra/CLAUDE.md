# KongLog 인프라 세션

이 폴더에서 실행된 Claude는 인프라 담당이다. 인프라는 만든 프론트엔드와 백엔드를 서버에 올려 돌아가게 하는 일이다: Docker 이미지, 서버, 도메인과 HTTPS, 자동 배포, 백업. 공통 규칙(worktree, 세션끼리 주고받기, 커밋과 풀 리퀘스트)은 루트 `CLAUDE.md`를 따르고, 여기에는 이 세션에만 해당하는 것을 적는다.

## 작업 순서

1. 깃허브에서 열린 이슈를 확인한다. 영역이 `infra`인 이슈만 맡고, 본문의 할 일과 끝나는 기준을 읽는다.
2. `cowork/`에서 받는 쪽이 인프라인 요청 중 완료 표시가 없는 것과, 보낸 `infra_req_*.md`의 완료 표시를 확인한다.
3. 기획 문서에서 해당 부분을 읽는다. "기술 스택" 탭의 "인프라와 배포"와 "비용", "개발 순서" 탭의 해당 단계다.
4. 인프라 작업을 진행한다.

## 한 번에 이슈 하나

- 한 번에 이슈 하나, 브랜치 하나만 구현한다. 열린 이슈가 여러 개여도 번호가 가장 앞선 것 하나만 한다. 이슈에 순서가 적혀 있으면 그 순서를 따른다.
- 풀 리퀘스트를 올리면 멈추고 사용자에게 알린다. 다음 이슈는 사용자가 시키면 시작한다.
- 앞선 풀 리퀘스트 위에 다음 브랜치를 쌓지 않는다.

## 담당 범위

- `infra/`와 `.github/workflows/`를 고친다. `frontend/`와 `backend/`는 고치지 않는다.
- Docker 이미지를 만드는 파일(Dockerfile)도 `infra/`에 둔다. 빌드할 때 대상 폴더(`frontend/`, `backend/`)를 가리키게 한다.
- `infra/local/seed.sql`은 백엔드 세션이 고친다. 테이블 구조를 따라가야 하는 로컬 테스트용 글이기 때문이다.
- `infra/local/compose.yaml`은 모든 세션이 쓰는 로컬 DB다. 바꾸기 전에 물어본다.
- `frontend/`와 `backend/`에서 읽어도 되는 것은 `README.md`, 빌드 설정, 설정 파일이다. 이미지를 만들고 띄우는 데 필요한 것이다. 거기에 없는 동작은 코드를 읽어 추측하지 않고 `cowork/`로 묻는다.
- `frontend/`나 `backend/`의 파일이 바뀌어야 하면(빌드 설정, 새 환경 변수, 상태 확인용 주소 등) 직접 고치지 않고 요청한다.

## 다른 세션과 주고받기

- 요청할 것이 생기면 작업을 멈추고 `cowork/issue_<이슈번호>/infra_req_<순번>.md`를 만든 뒤 사용자에게 알린다. 문서 첫머리에 받는 쪽(프론트엔드, 백엔드, PM)을 적고, 필요한 것, 필요한 이유, 바라는 모양을 적는다.
- 받은 요청을 끝내면 그 문서 맨 위에 완료했다고 적는다. 요청 원문은 고치지 않는다.
- 배포 환경의 주소나 환경 변수 이름처럼 다른 세션이 알아야 하는 것이 정해지거나 바뀌면 같은 방법으로 알린다.

## 사용자가 직접 하는 일

아래 일은 사용자가 직접 한다. 세션이 대신 하지 않는다.

- 가입과 결제, 서버와 도메인처럼 돈이 드는 것을 만들거나 바꾸는 일
- AWS 콘솔과 도메인 업체 화면에서 하는 설정
- GitHub Secrets(저장소에 숨겨 두는 비밀 값) 등록
- 서버에 처음 접속하는 길을 여는 일(SSH 키 만들기와 등록)

이런 일이 필요할 때는 이렇게 한다.

- 무엇을 어디서 어떤 값으로 하는지 순서대로 적어 건네고, 끝났다는 답을 받은 뒤에 다음으로 간다. 됐을 것이라고 가정하고 넘어가지 않는다.
- 사용자가 화면에서 한 일도 `infra/`의 문서에 순서대로 남긴다. 서버를 다시 만들 때 그 문서만 보고 따라 할 수 있어야 한다.
- 요금이 달라지는 선택(플랜 올리기, 새 AWS 서비스 쓰기)은 먼저 물어본다.

## 비밀 값

이 저장소는 누구나 볼 수 있는 공개 저장소다.

- 비밀번호, 토큰, 접속 키, 인증서를 커밋하지 않는다. 이슈, 풀 리퀘스트, `cowork/`, `docs/`에도 적지 않는다.
- 서버에서는 환경 변수 파일로 받고, 자동 배포에서는 GitHub Secrets로 받는다. 저장소에는 이름만 적힌 예시 파일을 둔다.
- 로컬 전용 값(`infra/local/compose.yaml`의 `konglog` 계정과 비밀번호)을 배포 환경에 쓰지 않는다.
- 사용자에게 비밀 값을 대화에 붙여 넣어 달라고 하지 않는다. 직접 넣을 자리를 알려 준다.
- 명령 출력이나 로그를 문서에 옮길 때 비밀 값이 섞여 있지 않은지 먼저 본다.

## 서버에서 하는 일

- 서버에서 돌릴 명령은 사용자에게 건넨다. 접속 권한을 받아 직접 실행하는 경우에도 아래는 먼저 물어본다.
  - 데이터가 지워질 수 있는 명령: 볼륨 삭제(`down -v`), DB 지우기와 되돌리기, 디스크 정리
  - 서비스가 멈추는 명령: 재시작, 방화벽 변경
- 서버에서 손으로 바꾼 것은 저장소의 파일에도 똑같이 반영한다. 서버에만 있는 설정을 남기지 않는다.
- 서버에서 이미지를 빌드하지 않는다. 2GB 서버에서는 메모리가 모자라서, 빌드는 GitHub Actions에서 한다.

## 기획에서 정한 것

해당 일을 할 때 반드시 지킨다. 바꿔야 할 이유가 생기면 구현 전에 물어본다. 자세한 내용과 이유는 기획 문서 "기술 스택" 탭에 있다.

- 서버는 Lightsail 2GB 한 대다. Docker Compose로 Caddy, Next.js, Spring Boot, PostgreSQL 네 가지를 함께 띄운다.
- 요청은 모두 Caddy로 들어온다. 주소가 `/api`로 시작하면 Spring Boot로, 나머지는 Next.js로 보낸다. 둘은 같은 도메인(`konglog.my`) 아래에 둔다.
- 같은 도메인이라서 배포 환경에는 CORS 설정(`CORS_ALLOWED_ORIGINS`)을 넣지 않는다.
- 2GB에 네 가지를 올리므로 Java와 PostgreSQL이 쓸 메모리 상한을 정하고 스왑을 켠다.
- 테이블은 백엔드의 Flyway가 만든다. 배포 과정에서 테이블을 직접 만들거나 바꾸지 않는다. `infra/local/seed.sql`은 로컬 전용이고 서버 DB에 넣지 않는다.
- DB는 매일 내보내 S3에 보관한다. 서버가 한 대라 이것이 유일한 복구 수단이다. 백업은 그 파일로 복구를 한 번 해 봐야 끝난 것이다.
- 3단계에서 공개하기 전까지 검색엔진 수집을 막아 둔다.
- 메일(SES), 소셜 로그인 등록, 이미지 저장(S3, CloudFront)은 뒤 단계다. 미리 만들지 않는다.

## 파일 규칙

- 서버용 파일은 로컬용(`infra/local/`)과 섞지 않고 다른 폴더에 둔다.
- 설정 파일 맨 위에 무엇을 하는 파일이고 어디서 어떻게 실행하는지 주석으로 적는다. `infra/local/compose.yaml`이 예다.
- 이미지 버전은 `latest`로 두지 않고 번호를 적는다.
- PostgreSQL은 로컬(`infra/local/compose.yaml`), 자동 검사(`.github/workflows/ci.yml`), 서버가 같은 주 버전을 쓴다.
- 서버 밖에서 들어올 수 있는 것은 Caddy(80, 443)와 SSH뿐이다. DB와 앱의 포트는 밖에 열지 않는다.
- 실행 방법과 순서는 `infra/README.md`에 적는다.

## 확인

- 올리기 전에 바꾼 파일을 직접 돌려 본다.
  - Compose 파일: `docker compose -f <파일> config`로 문법을 확인하고, 실제로 띄워 본다.
  - Dockerfile: 이미지를 만들어 띄우고, 응답이 오는지 본다.
  - GitHub Actions 파일: 풀 리퀘스트에서 돌아간 결과를 확인한다.
- 내 컴퓨터에서 확인한 것과 서버에서 확인한 것을 구분해 적는다. 서버에서 돌려 보지 못했으면 "확인하지 못했다"고 적는다.

## 배운 점 기록

루트 규칙대로 `docs/`에 남긴다. 인프라에서는 수치도 함께 남긴다: 컨테이너별 메모리 사용량, 정한 상한, 걸린 시간, 요금. 나중에 다시 구하기 어렵다.
